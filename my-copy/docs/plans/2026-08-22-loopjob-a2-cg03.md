# LoopJob crash recovery and at-least-once delivery

## Knowledge packet

- MENTAL_MODEL: a claimed job is not completed merely because a handler may have produced an effect. Completion is a separate fenced write; if the process disappears first, expiry makes the missing completion visible as retry or retained dead work.
- ASSIGNED_TEST_EVIDENCE: `A2-CG3-T1 crash-restart-recovery` first failed because closed-code and delivery behavior did not exist. Its four nested cases now prove exhaustive closed unions, effect-before-success crash and idempotent redelivery, final-attempt stale recovery to retained dead, and sanitized malformed/unknown/thrown delivery failures. The focused gate is 5/5 GREEN and the project suite is 364/364 GREEN.
- PROBLEM_CONTEXT: a process can crash before the handler, during it, or after an external effect but before recording success. Deleting the row loses debt; treating effect invocation as success loses retries; replaying blindly can duplicate effects; persisting caught messages can leak payloads, paths, commands, or tokens.
- EXECUTION_FLOW: recover at most one expired running row -> if attempts remain, set `retry_wait/availableAt=now`; otherwise set retained `dead/finishedAt=now` -> claim a due row -> reparse canonical payload and verify hash -> require an own registered handler with `job_id` idempotency -> invoke without a DB transaction -> fenced success or sanitized retry/dead failure.
- CODE_EVIDENCE: `src/lib/loop-jobs/raw-state-adapter.ts:100` performs stale recovery without incrementing attempts; `src/lib/loop-jobs/state-machine.ts:157` revalidates persisted payload bytes and hash; `state-machine.ts:241` schedules sanitized retry/dead and `state-machine.ts:410` records fenced success. `src/lib/loop-jobs/delivery.ts:40` separates queue delivery from the handler effect and exposes only closed outcomes.
- DESIGN_RATIONALE: at-least-once delivery is explicit because a local queue cannot atomically commit an arbitrary external effect and the job row. Passing job ID as the mandatory idempotency key lets handlers collapse redelivery. Closed last-error/result codes retain operational meaning without copying attacker-controlled material.
- REJECTED_ALTERNATIVES: marking success before the handler was rejected because a crash loses work. Marking success immediately after an effect with no fencing was rejected because a recovered owner may already exist. Deleting succeeded/dead rows was rejected because it erases audit debt. Persisting exception messages was rejected because they can contain secrets. Exactly-once claims were rejected because the external effect is outside the SQLite transaction.
- GUARANTEES: expired nonfinal work becomes immediately visible retry work; an expired final attempt becomes retained dead without an extra delivery; recovery does not increment attempts; malformed payload, unknown kind, and handler throw use closed sanitized errors; old lease completion is fenced; effect-after-crash can be redelivered while a job-ID-idempotent fake applies one effect.
- NON_GUARANTEES: external effects are not exactly once, handlers must implement their own idempotency, a hung handler is not reliably cancelled by the queue contract, and this slice does not provide scheduler, daemon, watchdog, or real domain handlers.
- CONCRETE_TRACE: attempt 1 claims job J with token T1. The handler adds external effect key J, then the process disappears before success. At exact expiry recovery sets `retry_wait`, `lastError=lease_expired`, and preserves attempts 1. A new claim increments attempts to 2 and calls the handler again with J; the idempotent set remains one effect. Fenced success with the new token retains the job as `succeeded` with `finishedAt`.
- CONCEPT_DELTA: the model changed from “handler ran, therefore work is done” to “handler effect and durable completion are separate; crash recovery deliberately accepts redelivery and makes idempotency part of the handler contract.”
