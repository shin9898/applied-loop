# LoopJob atomic claim and lease fencing

## Knowledge packet

- MENTAL_MODEL: observing a due row does not create ownership; only the single conditional write that installs a fresh lease token does. Every later mutation must prove that exact token is still unexpired.
- ASSIGNED_TEST_EVIDENCE: `A2-CG2-T1 concurrent-claim-and-fence` first reached claim/busy assertions but failed because renewal and recovery were absent. Its four nested cases now prove one process wins a simultaneous claim, renewal loses at exact expiry, renewal and recovery have one consistent winner, reclaimed work fences the old token, and SQLite busy becomes one bounded `storage_failure`. The focused gate is 5/5 GREEN and the project suite is 364/364 GREEN.
- PROBLEM_CONTEXT: two workers can read the same due work, and an old worker can finish after its lease was recovered and reassigned. Without an atomic claim and generation-specific fencing, one job can run twice as the apparent owner or stale completion can overwrite the new owner.
- EXECUTION_FLOW: bind injected `now` and new ownership values -> one `UPDATE ... RETURNING` selects and rechecks the first due row -> winner becomes `running` and increments attempts once -> renew/succeed/fail condition on ID, running state, exact lease token, and `leaseExpiresAt > now` -> zero changed rows become `lease_lost`; recovery separately rechecks the observed expired token and expiry.
- CODE_EVIDENCE: `src/lib/loop-jobs/raw-state-adapter.ts:34` performs the one-statement claim with deterministic ordering and outer eligibility checks; `raw-state-adapter.ts:71` renews only an unexpired token; `raw-state-adapter.ts:100` materializes one stale candidate and rechecks token plus expiry. `src/lib/loop-jobs/state-machine.ts:198` centralizes the unexpired ownership predicate used by success and failure.
- DESIGN_RATIONALE: SQLite already serializes writers, so a parameterized `UPDATE ... RETURNING` supplies the smallest reliable ownership boundary without holding a transaction across handler execution. A random lease token identifies a lease generation; job ID or worker ID alone cannot distinguish an old execution from a reclaimed one.
- REJECTED_ALTERNATIVES: JavaScript `findFirst` then update was rejected because selection and ownership are separate races. A deferred two-statement transaction was rejected because the installed adapter/runtime contract requires the proven single statement. Worker identity without a lease token was rejected because the same worker may reclaim later. Automatic busy retry/sleep was rejected because it hides latency and can spin.
- GUARANTEES: at most one claim winner per lease generation; attempts increment exactly once for the winning claim; renew before expiry extends the lease; renew at expiry loses; renewal versus recovery yields one state-consistent winner; old succeed/fail/renew calls return `lease_lost`; a busy database makes one bounded adapter attempt and returns a closed storage error.
- NON_GUARANTEES: the handler effect remains at-least-once, a lease does not cancel a still-running old handler, SQLite does not provide distributed multi-database ownership, and CG-02 does not activate any worker.
- CONCRETE_TRACE: workers A and B start separate Prisma clients at the same injected time against one due row. Both issue the same parameterized claim; SQLite serializes the writes, A returns the row with token T1 and attempts 1, while B returns `no_job`. At expiry recovery clears T1 and requeues; B later claims with T2 and attempts 2. A's completion using T1 changes zero rows and returns `lease_lost`, while T2 can terminally succeed.
- CONCEPT_DELTA: the model changed from “the worker that found the row owns it” to “ownership is a short-lived, generation-specific database fact that every write must re-prove.”
