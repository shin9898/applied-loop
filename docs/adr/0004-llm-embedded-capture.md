# ADR-0004: 登録は手動ではなく LLM ワークフロー埋め込みで自動化する

## 背景

ADR-0003 でループのアプリ内完結を決めたが、それでも「学びの登録」が
手動フォーム入力のままではハードルが高く、習慣化しない。
開発者が日常的に使っている LLM (Claude Code / Cursor 等) の会話の中に
こそ学びは発生しており、そこから自動で拾えなければ実質使われない。

## 決定

Applied Loop を **MCP サーバー**として LLM ワークフローに埋め込み、
学びの捕捉を自動化する。

1. **MCP ツール化**: `record_entry` / `record_application` /
   `suggest_cards` などを MCP ツールとして公開。
   ユーザーが LLM と作業中、LLM 側が「これは学び」と判断して記録する
2. **候補 → 確認フロー**: 自動で拾った学びはまず「受信箱 (Inbox)」に
   候補として入り、朝の確認で登録/無視を1タップで決める。
   全自動で正典化はしない（ノイズ混入を防ぐ人間のゲート）
3. **出典の記録**: 候補には必ず発生元（ツール名・日時・会話の文脈）を
   付ける。証跡の信頼性を担保するため
4. 手動フォームは残すが副次経路とする

## 理由

- my-copy の hook 設計（runtime-labelled events の捕捉）と同じ思想を、
  プロダクト側に持ち込む。開発者自身がこの自動化で恩恵を受けている
- 2026 年時点で LLM を日常使いするエンジニアは十分な市場規模であり、
  「LLM が秘書として学びを貯める」はその層に刺さる
- 却下案: 「ブラウザ拡張での記事クリップ」→ 読む学びは拾えるが、
  会話の中で発生する実践的な学び（デバッグの発見等）を拾えない。
  こちらが本プロダクトの差別化領域

## 結果・トレードオフ

- 得られるもの: 登録コストほぼゼロ / 習慣化の担保 / LLM 連携という明確な差別化
- 失うもの: LLM 非利用者には価値が届きにくい（当面は許容。
  ターゲットを LLM 日常利用エンジニアに明確化する）

## 出典

- ユーザーフィードバック (2026-08-01):
  「自身のLLMを使う過程で自動で貯まるみたいな自動要素を入れないと
  まず使われない」
