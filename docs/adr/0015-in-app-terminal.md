# ADR-0015: アプリ内ターミナルハーネスと外部公開時のセキュリティ設計

## 背景

開発者の体験構想 (2026-08-03 確認済み):

> アプリケーション側でターミナルを起動し、自身の契約 LLM と
> 該当のアクション内容をベストな形でやりとりできる UIUX。

ゲート回答時にアプリ内ターミナルパネルを開き、ユーザーの契約 LLM
(claude / codex CLI) をゲートのコンテキスト (質問・文脈再現・
リソース) プリロード済みで起動。LLM と対話しながら回答を練り、
MCP (`answer_gate`) でアプリに反映する。

これは「調査力を測る」思想 (v3) と完全に整合する:
**LLM と相談して作った回答は「調べて解いた」の最も自然な形**。
採点は引き続き独立ヘッドレス LLM が行うため迎合リスクは変わらない。

2026-08-04 追記: rate limit / Ctrl+C 後にセッションが死に、
普通のターミナルのように復帰できない問題が実利用で顕在化。
Fable レビューを経てライフサイクル原則を改訂した (本 ADR §1.1・§4)。

## 決定

### 1. アーキテクチャ (ローカルモード)

```
ブラウザ (xterm.js) ←→ WebSocket (localhost:3101) ←→ node-pty (claude/codex CLI 直起動)
                                                              ↓ MCP 呼出
                                                    Applied Loop (answer_gate)
```

- **フロント**: `xterm` + `xterm-addon-fit`。ターミナルパネル
  コンポーネント (ゲート詳細に展開)
- **ターミナルサーバー**: `scripts/terminal-server.mjs`
  (`ws` + `node-pty`、ポート 3101)。Next.js 本体とは別プロセス
  (App Router の Route Handler は WebSocket アップグレードを
  扱えないため)。`npm run dev` との同時起動は `concurrently` で
  `npm run dev:all` を用意
- **起動コマンド**: デフォルトは環境変数 `TERMINAL_SHELL_CMD`
  (claude / codex)。UI でも起動時・再起動時に選択可能
- **コンテキスト注入**: CLI 起動後、出力が落ち着いたタイミングで
  ゲートの質問・文脈再現・リソース一覧を初期入力として流し込む
  (再起動時も同じゲート文脈を再注入。`gateId` はセッション固定)
- **反映**: ターミナル内の LLM が applied-loop MCP の `answer_gate` を
  呼ぶ。採点は既存通り独立ヘッドレスで非同期
- `answer_gate` の `source: "terminal"` → `answerMode="assisted"`
  (self / researched / in_session に次ぐ 4 値目。NSM 影響なし)

### 1.1 セッションライフサイクル (2026-08-04 改訂)

| 事象 | 挙動 |
|---|---|
| CLI プロセス終了 (Ctrl+C / rate limit / 正常終了) | **WS は維持**。UI に再起動オーバーレイを出す |
| ユーザーが再起動を明示操作 | 同一 WS・同一 gateId で CLI を再スポーンし文脈を再注入。claude/codex 切替可 |
| WS 切断 (ページ離脱・パネル閉じ) | **pty を即殺**。再アタッチはしない |
| 自動再起動 | **しない** (rate limit 直後のクラッシュループを避ける) |

原則: **1 WS セッション = 1 ゲート文脈**。その中で CLI プロセスは
複数世代ありうる。`answer_gate` の紐付けは常に注入された `gateId`
に依存し、プロセス世代には依存しない (二重提出は MCP / アプリ側の
既存ガードに委ねる)。

### 2. セキュリティ (ローカルモード)

ブラウザからのシェルアクセスは最大級のリスクのため:

- **環境変数ゲート**: `ENABLE_TERMINAL=true` の時のみ有効
  (デフォルト無効。未設定なら UI にボタン自体を出さない)
- **localhost バインド**: ws サーバーは 127.0.0.1 のみ listen
- **認証**: ws 接続の初回メッセージで `MCP_TOKEN` を検証。
  トークンはログイン済みのアプリ画面からのみ取得できる
- **子プロセス環境の scrub**: WS 認証用 `MCP_TOKEN` は
  子 CLI の環境変数に渡さない
  (`APPLIED_LOOP_MCP_TOKEN` は CLI の MCP 認証に必要なので残す)
- **コマンド許可リスト**: pty で **spawn する先頭コマンド** は
  claude / codex / bash のみ

#### 許可リストの意味 (明文化・2026-08-04)

許可リストは **「WS 経由で spawn できる先頭コマンドの制限」** であり、
**実行サンドボックスではない**。`bash` を許可した時点で、その中で
任意コマンドを実行可能になる。ローカル・127.0.0.1・MCP_TOKEN 前提では
脅威モデルは「既にマシンにいる攻撃者」と同等であり、許可リストで
実行コードを封じているという安心感は誤り。公開時 (ローカルエージェント)
でも同じ定義を引き継ぎ、エージェント側で追加の制約
(セッションタイムアウト・監査メタデータ) を足す。

### 3. 外部公開時の設計 (将来)

クラウド公開 (マルチユーザー化) する場合、ローカルモードの方式は
成立しない (サーバー上でユーザーの LLM CLI は動かせない)。
以下の段階設計とする:

| モード | ターミナル |
|---|---|
| ローカル (現在) | 有効 (本 ADR §1-2)。CLI 直起動 + 再起動 UI |
| クラウド初期 | **UI 非表示** (`DEPLOY_MODE=cloud` でボタンを出さない)。ゲート回答は MCP 経由のみ |
| クラウド + エージェント | **ローカルエージェント方式** (下記)。**同一のライフサイクル原則** (CLI 直起動 + 再起動 UI) をエージェント側で再利用 |

ローカルエージェント方式 (クラウドでもターミナルを使えるようにする将来設計):

- ユーザーがローカルで `applied-loop-agent` を実行
  (ユーザーの PC 上で pty + LLM CLI を持つ小さなデーモン)
- エージェントは **アウトバウンド WSS** でクラウドに接続
  (NAT/ファイアウォール越え不要。VS Code Remote Tunnels /
  ngrok agent と同じパターン)
- **ペアリングコード認証**: 初回のみブラウザに表示された
  ワンタイムコードをエージェントに入力してアカウント紐付け
- ブラウザのターミナル UI ⇔ クラウド (中継) ⇔ ローカルエージェント
  (pty) の構成。クラウドは中継のみで **E2E 暗号化** (内容を復号しない)
- エージェント側でもコマンド許可リスト (spawn 先制限) +
  セッションタイムアウト + 監査ログ
  (いつ・誰が・どのゲートで開いたか。コマンド内容は記録しない)

これにより「ユーザーの LLM はユーザーのマシンで動く」
(BYO-LLM のプライバシー不変条件) をクラウド化後も維持する。

### 4. ローカル / 公開の単一方針 (2026-08-04)

ローカルと公開で体験を分岐させない。どちらも:

**CLI 直起動を維持し、プロセス終了後も WS (またはエージェント相当の
セッション) を保ったまま再起動 UI を出す。**

シェルを親にする二層設計は採らない (却下理由は §却下した案)。

## 却下した案

- **Next.js 内での WebSocket 統合** (カスタムサーバー化):
  App Router の運用を複雑化する。別プロセスで十分
- **フォーム復活 (対話なしの単発送信)**: 開発者の構想は
  「対話しながら練る」体験。フォームは補助として残す判断は
  別途 (本 ADR のスコープ外)
- **クラウド側での LLM CLI 実行 (コンテナ隔離)**: ユーザーの
  契約 LLM 認証情報をクラウドに置くことになり、
  プライバシー不変条件とセキュリティの両面で非現実的。
  ローカルエージェント方式を採る
- **ターミナル内容の録画・保存**: 会話本文はプライバシー不変条件の
  対象。監査ログはメタデータ (開始時刻・ゲート ID) のみ
- **シェルを親にして CLI を子にする (2026-08-04 却下)**:
  bash は既に許可リストにあり新規権限ではない。実質差分は
  「復帰 UX」と「文脈注入」だけで、構造変更なしに再起動 UI で
  足りる。プロンプト検知による注入は壊れやすく、デフォルトを
  シェル親にすると許可リストの意味がさらに曖昧になる。
  上級者がシェルを欲しければ既存の bash spawn で足りる
  (アプリはビューア寄り、本物のターミナルは手元に別にある)
- **CLI 終了時の自動再起動 (2026-08-04 却下)**:
  rate limit 直後にクラッシュループする。復帰は必ずユーザー操作
- **WS 切断後の pty 猶予・再アタッチ (2026-08-04 見送り)**:
  複雑さに対して現フェーズの見返りが薄い。WS 切断 = pty 即殺で固定。
  将来必要なら別途検討
