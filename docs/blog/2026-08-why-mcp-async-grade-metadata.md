# 生成AIで機能実装はできるのに仕組みを理解できてない、説明できない問題を、ローカルMCPループで解く — Applied Loopをつくった話

## この記事でわかること（先に結論）

**Applied Loop** は、AI コーディング中に起きる「動くけど説明できない」状態を、**チャットの外にも残る学習ループ**に変えるためのローカルアプリです。

役割分担はこうです。

| 層 | やること |
|---|---|
| **Claude / Cursor / Codex（MCP）** | 学びの記録、仕分け、しれんへの回答など「書く」操作 |
| **ぼうけんのしょ（Web ダッシュボード）** | 進捗の地図、未消化の問い、ずかんなど「見る」操作 |

設計の芯は次の三つです。理由は後半で書きます。

1. **操作は MCP に寄せる**（フォーム二重実装を避ける）
2. **回答の受理と採点を分ける**（チャット内 LLM の迎合を避ける）
3. **ハーネス観測はメタデータだけ**（会話本文は読まない）

対象読者は、Claude Code / Cursor / Codex を日常的に使い、「実装は速いが説明が追いつかない」感覚があるエンジニアです。セットアップ手順の詳細はリポジトリの案内ドキュメントにあります。この記事は **何の困りごとを解くか** と **なぜその形か** に絞ります。

---

## どんな困りごとか（ペイン）

### シーンでいうと

金曜日の午後、AI と一緒に機能をマージした。CI も通った。月曜のレビューで「ここ、なぜこの設計？」と聞かれて、うまく答えられない——ログはチャット履歴のどこかにあるはずなのに、探せない。あるいは、先週「わかった」つもりだったキャッシュの話が、別リポジトリで同じミスとして再発する。

これが、ここで言う **理解ギャップ** です。コードは出荷できる。でも次の場面で自分の言葉が足りない。

- コードレビュー・障害対応・面接で、意図を弁明できない  
- 「調べて通した」のに、調べた痕跡も結論も残っていない  
- 同じ種類の勘違いが、週をまたいで戻ってくる  

### なぜ、いま増えているか

AI 支援開発では、理解のギャップが定量的にも指摘されています。Anthropic の RCT（開発者 52 名、未知のライブラリ学習）では、直後の理解テストで AI 支援群の平均が手書き群より低かった、という報告がある（[Anthropic: How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills)）。本体側にも学習モードはありますが、だいたい **そのセッション内の説明** で終わりがちです。

足りないのは次の三つだ、と感じています。

| 足りないもの | 現場で起きること |
|---|---|
| **セッションを跨ぐ証跡** | 「あのとき何を学び、何を適用したか」がチャットの外に無い |
| **誤解の追跡** | 一度直したつもりが、別タスクで同じ穴に落ちる |
| **ツール側の見え方** | skill / hook / プロンプトキャッシュはログに出ているのに、学びとして使われない |

つまりペインは「AI が悪い」ではなく、**速度だけが先に行き、理解と記録の仕組みが置いていかれる**ことです。専用の学習アプリを開いてフォームを埋める、という解決は、一日の大半を LLM セッションで過ごす人には第二の仕事になりやすい——ここが設計の出発点でした。

---

## どうなればよいか（ゲイン）

Applied Loop が目指す状態は、次のような日常です。

| Before | After |
|---|---|
| 学びがチャットに散らばる | 非自明な知見だけ候補になり、仕分けて残せる |
| 「わかったつもり」が検証されない | しれん（理解度チェック）が残り、後から合否を見られる |
| 同じ勘違いが再発しても気づきにくい | ずかん（つまずき／誤解の一覧）で未解消や再発を追える |
| 今日のタスクと過去の学びがつながっていない | 朝の要約から、タスクと関連学びを結べる |
| キャッシュや hook の不調が感覚頼み | token やツール実行のメタデータから「見え方」を点検できる |

一言でいうと、ゲインはこれです。

> **AI で実装する速度を落とさずに、説明できる理解と、適用の記録が同じペースで残る。**

「教材サイトを読む時間」を増やすプロダクトではありません。**自分の作業（コミット・セッション・タスク）を、理解の材料に再利用する**側です。API キーをプロダクトに渡してクラウド学習させるのではなく、手元の LLM とローカル DB で回す前提です（いわゆる BYO-LLM）。

## つくったもの: 全体像

### 二層構造

```
[ LLM セッション ]
  MCP で書く・仕分ける・答える
        │
        ▼
[ ぼうけんのしょ（Web ダッシュボード） ]
  見る・診断する・進捗を把握する
```

- **書く場所**をチャット（MCP）に置く → いつもの作業の延長で記録できる  
- **見る場所**を Web に置く → 地図や一覧など、Markdown だけでは弱い可視化を担当する  

UI には RPG 風の呼称がありますが、意味は括弧のとおりです。

| UI 上の呼び方 | 意味 |
|---|---|
| ぼうけんのしょ | Web ダッシュボード全体 |
| しれん | 理解度チェック（出題） |
| じゅもん | アプリ内から LLM／MCP を開く導線 |
| ずかん | つまずき／誤解の一覧 |
| じゅんび | セットアップ診断画面 |

いまはセルフホストで、自分で使いながら検証している段階です。不特定多数向けのアカウント認証は、公開募集の直前でよいと判断しています。

### 一日の最短ルート

1. **つなぐ** — アプリを起動し、MCP 用の共有トークンを用意し、使う LLM に MCP を登録する  
2. **集める** — ルールに「朝は要約、気づきは候補登録」と書き、git hook でコミットを送る（そこからしれん生成につながる）  
3. **進める** — 朝に要約を取り、未消化のしれんを解き、必要なら「この学びを使った」を記録する  

準備が足りないときは、ホームに案内が出て、じゅんび（セットアップ診断）で何が欠けているかが見えます。しれんは Web の解答画面でも、チャットの MCP からでも解けます。

### 主なループ

- **しれん（理解度チェック）** — 用語の暗唱ではなく、「自分の言葉で説明できるか」を問う  
- **学びの受信箱** — 非自明そうな知見を候補化し、残す／捨てるを仕分ける  
- **ずかん（つまずき／誤解の一覧）** — 未解消の穴や、一度解消したあとの再発を追う  
- **タスクと学びの対応** — 今日の仕事と、関連する過去の学びを結ぶ  
- **ハーネス観測** — モデル・token・ツール実行などのメタデータから、キャッシュや hook の様子を見る（会話本文は見ない）

## なぜ、この三つの設計にしたか

上のペイン／ゲインを成立させるために、意図的に捨てたものがあります。

### 1. 操作は MCP に寄せる（フォームを正にしない）

**結論:** 書き込みの入口を MCP にそろえないと、説明も実装も二重になる。

同じ「しれんに答える」「受信箱を仕分ける」を、Web フォームと MCP の二経路で持つと、次が起きます。

- どちらが正しい手順か、ドキュメントが割れる  
- 受理条件・採点の起動タイミングがズレる  
- 「アプリではできた／ツールではできない」の調査が増える  

なので、学びの新規登録フォームは廃止し、MCP（またはじゅもん＝同じ LLM／MCP 経路）へ寄せました。Web の解答画面は「すぐ書きたいとき」の shortcut として残していますが、**裏の受理処理は MCP 経由と同じ一本の道**です。見た目の入口は複数でも、状態遷移は一本、というのが実務的な「一本化」です。

### 2. 回答の受理と採点を分ける

**結論:** 合否をチャットのその場で返すと、しれんが自己採点の劇場になりやすい。

チャット内の LLM に「今の答えで合格か？」までやらせると、先回りして言い換えたり、慰めたり、部分点を盛ったりしがちです。なので境界を分けました。

1. **受理** — 回答を保存するだけ。ここでは合否を返さない  
2. **採点** — 別プロセスの LLM が、セッションの外で採点する  
3. **確認** — あとから結果を取るか、ダッシュボードで見る  

「受け付けた」と「通った」を同じターンに混ぜません。出題の意図も、用語暗唱ではなく **概念を自分の言葉で説明できるか**（必要なら調査した痕跡があるか）です。

### 3. ハーネス観測はメタデータだけ

**結論:** 会話本文を集めると、プライバシーも勝ち筋も別物になる。

skill / hook / プロンプトキャッシュの改善も重要なテーマです。ただしプロンプトや回答本文、コード断片まで吸い上げると、

- ローカル運用の信頼が落ちる  
- 「セッション内容を要約して教えるサービス」と同じ土俵になる  

ので、集めるのはモデル名、token 内訳、ツール名、時刻、セッション ID、リポジトリなど **メタデータだけ** にしました。会話本文は読みません。改善提案は強制書き込みせず、本人が「適用した」と記録する形です。長い教材をアプリ内に複製するのも避け、観測と「本人への問い」に寄せています。

### 三つの判断は一本の線

```
書く場所をチャット（MCP）に寄せる
  → 採点をチャットの外に出す（迎合を断つ）
    → 観測はメタデータだけにする（信頼と差別化を守る）
```

守りたいのは、動いたコードの隣に、**説明できる理解**と**適用の記録**が残ることです。

## まとめ

- **ペイン:** AI で実装は速いのに、説明・証跡・誤解の追跡が置いていかれる  
- **ゲイン:** いつもの LLM 作業の延長で記録し、ぼうけんのしょで進捗と穴を見える化する  
- **形:** 書く＝MCP、見る＝Web。ローカル＋手元の LLM  
- **設計:** MCP 寄せ／採点分離／メタデータのみ  

試す場合はアプリを起動したあと、じゅんび（セットアップ診断）で準備を確認する。朝の要約・しれんへの回答・適用の記録は、いつもの LLM から MCP 経由で行う。

フィードバックや「この場面のペインが足りない」があれば歓迎です。
