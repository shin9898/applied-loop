01

契約の沈黙する欠落

ひとことで言うと: 「型が同じ」≠「どっちの組み立て経路も、その値を載せている」。 片方だけ直すと、もう一方は空のまま通ってしまう。

画面に出す1つの項目（例: 職種名）は、DB取得 → 変換 → API/画面、と何段も通る。 途中のどこかで詰め忘れても例外は出ず、空文字のまま「動いているように」見える。今日の材料は、その穴を両経路に塞いだ日。

  • 初学者が覚える一手: フィールドを足したら「同じ契約を組み立てている関数」を全部探す。
  • テストは空だけ通すと足りない。「実値が最後まで残る」ケースを1本は書く。

実務レイヤ · ミドル以上

失敗モードは false negative: ゼロ値と詰め忘れが区別できない。Consumer-Driven Contract や OpenAPI required、経路一元化（生成）のどれに担い手を置くかを選ぶ。コメント相互参照は再発防止としては弱い。

  • 担い手候補: 契約スナップショット / 変換の単一関数 / 必須の型表現
  • 残るリスク: E2E や本番観測でしか見えない分岐（権限別レスポンスなど）

02

正典と配布物のドリフト

ひとことで言うと: 「ドキュメントが正しいと言っているもの」と「いま動いているもの」と「配られたコピー」は、放置すると別物になる。

ルールに「正典は A」と書いてあっても、A が止まっていることがある。さらに配布用のコピーを手で直していると、再生成した瞬間に直した内容が消える。どちらも、上書きや障害のときまで気づきにくい。

  • 初学者が覚える一手: コピーを直したくなったら、まず本家（生成元）を探す。
  • 暫定で切り替えたら、「いつ・何を条件に戻すか」を切替場所に1行残す。

実務レイヤ · ミドル以上

検知は最終稼働時刻・滞留件数・完了率などの閾値。下流編集を拒否するなら差分チェックやマーカー検証。IaC の drift detection と同型の問題。

  • 還流: 下流の加筆を先に本家へ取り込み、その後に再生成
  • 可逆性: フラグや日付付きの復帰条件を、切替コミットに同居させる

一次情報（手元の根拠 → 公式/定番）

  • COMMIT 21fdd90 · 起票先切替（Hermes dormant） DIFF 手元の変更。本家と配布の関係を追う入口。
  • DOC Terraform: plan（drift 検知の一般形） OPEN 公式doc。「宣言と実態の差分を機械で見る」の型。
  • DOC Single source of truth OPEN 正典を一つに決める、という一般概念の入口。
03

安定プレフィックスと一時メモ

ひとことで言うと: キャッシュが効く系では「前半を変えにくい」。だから一時メモを先頭に書くと、得するはずが損しやすい。

プロンプトキャッシュなどは、先頭から同じ文字列が続いている範囲だけ再利用できる、と思っておくとわかりやすい。 「今週のメモ」を一番上に足すと、その後ろまで再計算になりやすい。禁止するだけだと現場は破るので、逃がし先を用意する。

  • 初学者が覚える一手: 毎回読む共通ファイルの「上半分」に日付付きメモを足さない。
  • 逃がし先例: 「可変」節の下、または条件付きで読む別ノート。

実務レイヤ · ミドル以上

境界は見出しマーカーやファイル分割で機械可読にする。lint / CI / 週次の先頭ハッシュ比較で検知。観測は cache read 率や先頭領域の変更頻度。今日の材料では workbench の read 率が前週比で低下している。

  • 規約だけより、壊れたときに赤くなる地点を1つ置く
  • OBS: workbench 今週 48.6% / 先週 55.0%

一次情報（手元の根拠 → 公式/定番）
