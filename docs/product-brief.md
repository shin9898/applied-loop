## 背景 — なぜピボットしたか

市場調査 (2026-08-01) の発見:

- **ペインは実在し定量化されている**:
  Anthropic RCT (2026-02, n=52) で AI 支援開発者はコード理解テスト
  50% vs 手書き 67% (17pt 差)。最大のギャップはデバッグ。
  "comprehension gap" / "epistemic debt" / "comprehension debt" が
  通用語になった
- **本体側が吸収し始めている**: Claude Code Learning output style
  (TODO(human) / Insight ブロック / Checkpoint Question)
- **勝ち筋**: 本体機能はセッション内で完結し、証跡が残らない・
  復習できない・誤解パターンが貯まらない。ここが差別化の核

競合調査 (2026-08-02 第2回) の発見:

- **vibe-learn** (gkaria/vibe-learn): Claude Code / Codex / OpenCode の
  セッションをフックで監視し、自動ブリーフィング (何が変わったか/
  どこを見るべきか)・ファイルツアー・学習キュー・Obsidian 連携。
  コンセプトが近似 ("outsource thinking, not understanding")
  → セッション内容の「説明」で終わる点が差別化余地
- **EngramQuest**: Obsidian ネイティブの AI 学習レイヤー。
  ノート → クエストマップ / FSRS-5 デッキ / メモリマップ。
  BYO-LLM (Claude Code / Cursor 等のローカル AI に Skill 注入)
  → 「ノート → 教材化」が本業。Obsidian プラグイン開発は戦わない
- **Vibe Sensei / VibeUniv / Unvibe / Pear**: コミットのフラッシュ
  カード化、深さに応じた説明、知識ギャップ追跡
- **gamification の教訓**: Duolingo は外発的 (ストリーク/リーグ)、
  Boot.dev は「進捗 = 実スキル」のリアル gamification、Brilliant は
  内発的報酬 (desirable difficulty) のみ。Applied Loop は Boot.dev /
  Brilliant 側に立つ (ストリークは主役にしない)
- **誤解のライフサイクル管理 (open→resolved→regressed をゲートで
  検証し続ける) は競合にない独自資産**。ここを伸ばす

## Who — 誰の課題か

- 一次: **新しい領域に挑戦するエンジニア**（AI コーディングを日常的に使う）。
  ユーザー #1 = 自分（一次体験者。「実装できるが中身を説明できない」を自覚）
- 二次: プログラミング初学者（一次で回ってから迎えにいく）
- v3 補足: 一次体験者にとって **AI ハーネスそのものが最大の新領域**。
  「ただ使っている」状態から「仕組みを理解して使いこなす」状態への
  移行も、このプロダクトが解く課題に含める
- v4 補足: 一次体験者は **LLM セッション中心の生活**をしている。
  専用アプリを開いて操作する行為自体が friction であり、
  アクションは会話の中で完結する必要がある

## JTBD — 雇われる仕事

**AI で実装しながら、自分の理解も同じ速度で育てたい。**

「動くが読めない」「出荷できるが説明できない」状態から抜け出し、
面接・レビュー・障害対応で「自分のコード」を弁明できる状態を取り戻す。

副次:
- 会話の中に散らばる学びを逃さない（旧版から継続）
- 誤解しがちな概念のパターンを自覚する
- **ハーネス (skill / hook / rule / コンテキスト設計) の理解を深め、
  自分のハーネスを改善できるようになる** (v3 追加)
- 学びを外部発信（Qiita/Zenn）に転換する

## Why — なぜこのプロダクトか

- LLM 本体の学習モードは「その場の説明」まで。証跡・復習・
  誤解パターンの蓄積がない。理解はセッションを跨いで育つもの
- ユーザーの LLM を連携する BYO-LLM + ハーネス制御により
  API コストゼロで実現できる（組み込み AI はコスト的に非現実）
- 自分は pm-learn / my-copy で捕捉と習慣化を検証・運用済み
- **ハーネスの観測データ (token / skill / hook の実行記録) は
  既にローカルに吐かれているのに、誰も「学び」に変換していない** (v3)
- **ユーザーの実作業 (コミット) が教材なので、学習コンテンツを
  作る必要がない**。Brilliant / Boot.dev がコンテンツに投資する
  領域を、自分の作業の再利用でゼロコストにできる (v4)

### 考え方 — 認知の 4 象限 (v3 追加)

プロダクト全体の哲学として、理解の状態を 4 象限で捉える:

| 象限 | 状態 | Applied Loop の働きかけ |
|---|---|---|
| 未知の未知 | 知らないことすら知らない | **減らす**: ゲート・ハーネス観測が「知らないことの存在」を可視化する |
| 知の未知 | 知らないと自覚している | **知の知に**: 誤解として記録し、反復で解消していく従来ループ |
| 未知の知 | 実はできているが自覚していない | **知の知に**: 「調べて解けた」等の行動を記録して自覚化する |
| 知の知 | 知っていると自覚している | **維持する**: 忘れる頃の再出題で定着を確認する |

「理解のギャップを埋める」よりも、**まず未知の未知を減らし、
ちょっとずつ各象限を知の知へ引き上げる** のがこのプロダクトの姿勢。

## 形態 (v4 新設) — アクションは AI 経由、表示はドキュメント

**アプリ上でアクションしない。アクションは全て生成AI (MCP) 経由で
LLM セッション内に集約し、アプリは「見やすい読み取り専用
ダッシュボード」に縮小する。**

開発者の実態: 一日の大半を LLM セッション (Claude Code / Cursor /
Codex) で過ごし、Obsidian を第二の脳として運用している。
「アプリを開いてフォームを操作する」体験はこの行動様式から外れており、
機能を積み上げても使われない。

| 層 | v3 まで | v4 |
|---|---|---|
| アクション (回答・登録・承認) | アプリのフォーム UI | **MCP ツール経由で LLM セッション内に集約**。アプリからアクション UI を撤去 |
| 閲覧 (リッチな可視化) | アプリ | アプリ (読み取り専用) に集約。ヒートマップ・図鑑・4象限マップなど MD では表現できないもの |
| 閲覧 (日次の確認) | アプリ | **Obsidian ダイジェスト (MD)** として生成し、日々の確認は vault で完結 |

- Obsidian 連携は `my-copy-obsidian-capture` の導線に乗せる
  (vault の学習ダイジェスト領域へ日次/週次 MD を生成)
- Obsidian プラグインは開発しない (EngramQuest 等の領土。
  車輪の再発明を避ける)。生成するのは MD ファイルのみ
- 「どこでも見えるミラー」としての読み取り専用 Web ダッシュボードは
  残す (localhost)。リッチな可視化の置き場所

## コアループ — 理解度ゲート + ナレッジ蓄積

実装の区切りで「自分のコードについての理解」を試すゲートが発火し、
回答・判定・誤解概念がナレッジとして貯まる。

### ゲートの思想 (v3 修正・v4 維持)

**「記憶テスト」ではなく「概念理解 + 調査力」を測る。**

エンジニアの実務は「正確に記憶していること」ではなく「正確に調べられる
こと」が本質。初学者ターゲットとも整合する。

- ゲートが問うもの: 概念の本質（「なぜこの設計か」「何を防ぐか」）
- **参考リソースは出題時から常時提示**（自己申告制折りたたみは廃止）
- **アクセスを自動記録**し、「自力回答 / 調査後回答」の区別を付ける。
  「調べて正解」も合格

### 採点の一本化 (v4) — SR カード廃止

v3 まで併存していた SR カード (0-5 自己採点・記憶重視) は
**ゲートの思想と矛盾するため廃止**する。

- 既存 SrCard は Gate 形式へ移行（question/answer をゲートの
  targetConcept/question に変換し、再出題スケジューラに乗せる）
- 反復間隔は採点結果に応じた可変間隔（強い正解は間隔を伸ばす。
  旧 v1.5 計画を前倒し）
- 以後、採点は全て LLM (ルーブリック) に統一。自己採点 UI は残さない

### 文脈再現 (v4 新規・E)

ゲートが出る頃にはコミットの文脈を忘れている。
回答前の認知負荷を下げるため、出題時に LLM が
**「このコミットでやったこと」の 2-3 行要約 (contextSummary)** を
同時生成して保存し、質問と共に表示する。
(リソースリンクは「調べる場所」、文脈再現は「前提の思い出し」で別物)

### 誤解の根因分類 (v4 新規・F)

採点時に LLM が誤解の根因を分類して記録する:

- `knowledge`: 知識不足（そもそも知らなかった）→ インプット強化
- `verification`: 確認不足（AI/ハーネスの出力を鵜呑みにした）→ ハーネス改善
- `premise`: 前提の誤認（状況理解がズレていた）→ 要件設計の見直し

誤解図鑑に「あなたの誤解の傾向」として分布を表示し、
図鑑を「コレクション」から「診断」に格上げする。

### 設計要件 (v3 から継続)

1. **ゲートの再帰**: 合格したゲートも忘れる頃に再出題する
2. **誤解パターンの資産化**: 「自分が誤解しがちなパターン」を可視化
3. **発火点のハーネス設計**: 「いつ発火するか」が製品の生死を決める
4. **リソース推薦の内製化**: 一次情報を出題時に同時生成
5. **ルーブリック採点**: 観点別評価と部分点
6. **調査力の記録**: 「調べて解けた」を合格として認める

### 弱点パターンの可視化 (v4 新規・H)

ルーブリック観点別スコアを横断集計し、「この観点はいつも欠ける」
という傾向を可視化する。個別ゲートの採点で終わらせず、
次に学ぶべきことの優先順位付けに使う。

### 回答サーフェス (v4 再検討)

v3 までは「出題・回答・採点はアプリ側」(Fable 条件 1) だったが、
v4 の形態転換に伴い **回答の受け付けも MCP ツール経由
(LLM セッション内) を許可する**。

Fable 条件 1 の懸念への対処:

| 懸念 | 対処 |
|---|---|
| 会話履歴に答えがある (カンニング) | v3 で思想が「記憶テスト → 概念理解+調査力」に変わり、リソース参照は推奨する設計。会話履歴もリソースの一種とみなす。ただし `answerMode="in_session"` を記録して区別可能にする |
| 採点 LLM の迎合 | **採点は引き続きヘッドレス CLI で独立実行** (変更なし)。会話中の LLM は回答の「受理」のみ行い、合否を言わせない |
| 構造化データとして計測不能 | MCP ツールの引数として回答を受け取るため構造化される |
| プロジェクトルールとの衝突 | hook の注入は「ゲートが出ています」の 1 トリガーまで (変更なし) |

## タスク起点ビュー (v4 新規) — 「今日の問いかけ」の転換

v3 までの「今日の問いかけ」は **学び起点** (「この概念を今日の
タスクで試せそう?」) で、ユーザーに「どのタスクで使うか」の
推理を強いていた。v4 では **タスク起点に逆転** する:

- 朝ブリーフィング時に今日のタスク (Hermes / TODO / 予定) を取得
- タスク × 関連する学び (Entry)・未解消の誤解 (Misconception) を
  LLM がマッピング
- ダッシュボードと Obsidian ダイジェストに
  **「今日のタスクと、それに関係する学び」** として提示
  （「タスク X には学び Y と未解消の誤解 Z が関係する」）

## 目標 (v4 改訂) — Goal OS ハーネス化

v3 の手動登録フォーム (title/period/kdi) は二重管理で friction のため廃止。
ユーザーの H2 目標は Goal OS (Obsidian) に既に存在する。

- **登録**: LLM セッション内で「H2 目標を読んで登録して」→
  MCP ツールが Goal OS ドキュメントを読み → Goal / KDI /
  紐付け対象ドメインを構造化提案 → ユーザー承認 → 登録
- **表示**: 証跡の密度と種類 (学び N・適用 M・誤解解消 K) +
  週次の定性評価。**進捗率は出さない** (変更なし)
- **紐付け**: 手動 + LLM 提案の確認制 (v1)、高信頼度は自動承認 (Phase 2 以降)
- **カスタマイズ**: 目標ごとの KDI・注力ドメインは LLM との対話で
  いつでも調整可能にする (ハーネス化の本質)

## ハーネス理解ループ (v3 追加・v4 で Phase 3 前倒し)

生成 AI を使うエンジニアは「ただ使う」だけではなく、**どのハーネスを
どうすれば良くなるか、一次情報のどこを読めばいいか**を理解して
改善していく必要がある。

- **観測**: Claude Code の `~/.claude/projects/*.jsonl` 等から
  メタデータ (モデル / skill・hook・rule / token 内訳 / 実行時刻) を
  増分収集。**会話本文は読まない** (プライバシー不変条件)。
  収集は全プロジェクト横断 (`HarnessRun.repo`)
- **学びへの変換**: token の偏り・誤解の兆候 (同じ指示の繰り返し等) を
  検出し、**誤解概念として Inbox に流す** (コード理解と同じ仕組み)。
  検出は全体合算に加え **repo 単位**でも行う (ADR-0016)
- **正典モジュール**: 観測グラフの「読み方」となるハーネス概念
  (第1号: プロンプトキャッシュ) を短い原理ページ + module ゲートで提供。
  **概念は横断、証拠と処方は局所 (repo)** (ADR-0016)
- **改善のネクストアクション**: 「どのハーネスをどう変えるか」の提案 +
  一次情報への導線。改善 → 再観測でループを閉じる
  （共有パック + repo 別 advisory 処方 — ADR-0017）
- 詳細は ADR-0009 / ADR-0016 / ADR-0017

## Inbox 自動トリアージ (v4 新規・G)

アクションの MCP 集約とハーネス観測の追加で Capture 候補が増えるため、
手動 accept/skip は破綻する。

- LLM が候補を重要度スコアリング (根拠つき)
- 高信頼度は自動 accept (GoalLink の `llm_auto` と同じ段階導入パターン)
- 低信頼度のみ確認待ちに残す
- 自動 accept の誤りは「取り消し」で戻せる (トリアージは可逆)

## 4象限マップ (v4 新規・D・Phase 3)

認知4象限の**状態遷移**を可視化する (競合にない独自機能):

- 週次の象限間の流れ: 「未知の未知が N 件発見され (ゲート不合格・
  ハーネス観測)、M 件が知の知に移動 (誤解解消・自力回答)」
- 理解の地形ヒートマップの上位レイヤーとして、
  「今週どれだけ未知を減らせたか」を示す

## 音声ダイジェスト (v4 新規・C・v4.1)

release-video パイプライン (VOICEVOX さやか) の資産を転用し、
週次の学びダイジェスト (解消した誤解・象限の変化・来週の焦点) を
音声化する。通勤中に「自分の学びの週次レビュー」を聞く体験。

- **前提: release-video パイプライン自体のブラッシュアップが必要**
  (開発者認識)。Applied Loop 側はダイジェスト MD の生成までを責務とし、
  音声化はパイプライン側の改善とセットで進める
- 楽しさ = 継続の燃料。競合の音声化 (NotebookLM 前提) との差別化は
  キャラクター性

## メテオフォール品質保証ループ (v4 新規・B・v4.1)

要件 (人間) → 実装 (AI 委譲) → ゲートで理解確認 → 合格したら次の要件へ、
という閉ループ。委譲した実装の理解をゲートが担保する =
「vibe coding しても comprehension debt を残さない開発プロセス」の完成形。
v2 計画の「メテオフォール要件定義」とゲートを統合する。

## NSM (変更なし)

**解消された誤解数 (週次)**

誤解 (Misconception) のライフサイクル: `open → resolved → regressed`

- `open`: ゲート初回不合格で記録
- `resolved`: 初回不合格から **72 時間以上あけた** スケジューラ起点の
  再出題に合格
- `regressed`: resolved 後の再出題で再度不合格 → open に戻る

「自力 / 調査後 / セッション内回答」の区別は記録のみで
NSM の計算には影響させない (v4 の `in_session` も同様)。

**先行指標 (立ち上げ期のみ併記)**:

- ゲート回答率 (回答 / 発火): 発火点と問題品質の診断
- 新規 open 誤解数: NSM の分母が貯まっているか
- ※ 立ち上げ 4 週間後に先行指標は診断ページへ降格する（サンセット条項）

## 採点の信頼性設計 (変更なし)

- **認証切れ**: リトライせず保留 (pending) + ユーザーに通知
- **JSON パース失敗**: スキーマ固定の出力指示 + 寛容パース + 再試行 1 回
- **最終フォールバック**: `self_graded` フラグ付きのセルフ採点
- **ルールベース採点への自動フォールバックは禁止** (NSM 汚染防止)
- **ルーブリック出力の欠落**: 合否のみで記録し観点データは欠損扱い

## 成功の定義 (8 週間)

- 自分がゲートをスキップせず回答している（回答率 5 割以上）
- 誤解パターンが 10 件以上 open になり、うち複数件が resolved している
- 同じ誤解での regressed が繰り返されない
- 目標ダッシュボードで「動いている実感」を週 1 回以上感じている (v3)
- **アプリを開かずにアクションが完結している** (v4 追加。
  セッション内での回答・登録・承認が成立している)
- **Obsidian ダイジェストを日次で開いている** (v4 追加)

## 旧版資産の継続利用

Inbox / Entry / Application / Experiment の資産は
ナレッジ層にそのまま転用する。**SrCard は Gate に移行して廃止** (v4)。
朝のブリーフィング (morning_briefing) はゲート通知と
タスク起点ビューの導線として主役化する。

## やらないこと

- AI 組み込み（API コストのため。BYO-LLM のみ）
- ユーザーのプロジェクトルールの上書き・大量注入
  （安定プレフィックスの共有パックと repo 別処方は **差分提案のみ**。
  強制書き込みはしない — ADR-0017）
- コード断片のクラウド保存（参照と概念のみ）
- ルールベース採点（NSM 汚染防止）
- チーム機能・共有機能（公開は個人利用が回ってから）
- タスク管理（正典は koki-central。Hermes Kanbanは2026-08-12廃止済み）
- 目標の「進捗率」の数値化 (v3。証跡の密度と定性評価で代替)
- ハーネス会話ログの本文解析 (v3。メタデータのみ収集)
- **汎用 SRS アルゴリズムの自前強化** (v4。FSRS の領土。
  反復はゲートの可変間隔で十分)
- **Obsidian プラグイン開発** (v4。EngramQuest 等の領土。
  MD 生成に留める)
- **外発的 gamification の強化** (v4。ストリーク・リーグは
  Duolingo の領土。残すが主役にしない)
- **学習コンテンツの作成** (v4。ユーザーの実作業が教材。
  ただしハーネス領域は、ユーザーの実作業＝ハーネス利用そのものであり、
  観測データを教材化する正典モジュールを Phase 3 に含む — ADR-0016。
  記事全文のアプリ掲載は引き続き非目標。
  トークン節約の実行層（共有パック + advisory 処方）は ADR-0017）
- **内部ドメイン用語の UI 露出** (v4。「適用」等のモデル名を
  そのまま表示しない。意味が自明な表現を使う)
